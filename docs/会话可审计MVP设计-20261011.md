# AgentLink 社会层升级 — 会话可审计 MVP 设计

> 版本：v0.1（设计稿，待评审）｜ 日期：2026-10-11
> 上游现状：AgentLink v0.1.5（本地 = 上游 GitHub，无版本差）
> 定位：**这是「社会层」升级的第一刀，不是通联层改造。**
> 关联：README「多智能体协作的开放问题」节 + 《AgentLink 公网化升级路线-20260930.md》

---

## 〇、一句话

**给 AgentLink 的每一次加密会话，加一本「不可篡改的账本」——记录密钥协商、加密降级、对端身份是否可信，且用 DID 签名封存。**

它解决的问题就一个：**降级静默**。

---

## 一、为什么先做这一刀（问题从哪来）

### 1.1 真实触发点：10-09 联机日志里的一行

```
📨 node-a [1] 收到: "🔒2EvQJMAuqpgPRZhK+c8vGlDyf+5+qdj1Ve9suVpbse8h56Meq7r7FOUR"
⚠️ node-a: 棘轮解密未命中，回退普通解密 [1]
🔓 node-a: 解密 [1] → "@search 贪污"
```

**这行 `⚠️ 回退普通解密` 是问题的核心：**

- 棘轮（逐消息独立密钥）本应命中，但**没命中，静默回退到普通解密**
- 通信**成功了**，但**安全性掉了档**
- 全程**无记录、无告警、无协议约定**——事后没人知道这次掉过档

这就是 Anthropic《Patterns and problems in multiagent systems》指出的
「agent 没有声誉可失、没有法庭可上诉、没有记得它的同事」在**最小尺度上的复现**：
**一次降级发生了，但系统"不记得"。**

### 1.2 为什么它是"社会层"问题，不是"通联层"问题

| | 通联层（路①） | 社会层（路②） |
|:--|:--|:--|
| 关心 | 消息能不能到、加不加密 | 降级了谁负责、能否追责、能否上诉 |
| 10-09 那行日志 | ✅ 消息到了（通联 OK） | ❌ 掉档了但无人记得（社会层缺失） |

**通联层已经够用**（尤其私网场景），**社会层是真空**。而"记得"，是所有社会机制的地基——
没有记录，后面的**仲裁 / 声誉 / 反合谋**全都无从谈起。

---

## 二、MVP 目标（做最小可用的一版）

**做：**
1. 每次会话，生成一本**结构化会话账本**（session ledger）
2. 记录**四类关键事件**：握手、加密档位、降级、挂断
3. 账本用**双方 DID 签名**封存（不可单方篡改）
4. 提供**只读查询**接口：给一个 session_id，能取回完整账本

**不做（明确划在 MVP 外）：**
- ❌ 实时告警 / UI（先有数据，再谈呈现）
- ❌ 跨会话的声誉聚合（那是第二步）
- ❌ 仲裁协议（第三步，依赖前两步）
- ❌ 改传输层（明文/TLS 是路①的事，本文不碰）

> **判据（什么样算 MVP 成功）**：跑一次真实跨机会话，
> 事后能凭 session_id 查出一本账本，账本里**明确写着**"本次是否降级、降了几条"。
> —— 10-09 那个"静默回退"从此**有据可查**。

## 三、数据结构设计

### 3.1 会话账本（Session Ledger）

一条会话 = 一个 JSON 对象，追加式（append-only）：

```json
{
  "ledger_version": "1.0",
  "session_id": "zh-6e3553ba",
  "initiator": "did:agentlink:node-a:qMX70FdXri1uZSdy",
  "responder": "did:agentlink:node-b:Z1Rd+LemnMSJZT8/",
  "channel": "ws",
  "started_at": "2026-10-09T21:09:12+08:00",
  "events": [
    {
      "seq": 0,
      "ts": "2026-10-09T21:09:12+08:00",
      "type": "handshake",
      "detail": {
        "kex": "X25519",
        "cipher": "ChaCha20-Poly1305",
        "sig": "Ed25519",
        "did_verified": true
      }
    },
    {
      "seq": 1,
      "ts": "2026-10-09T21:09:14+08:00",
      "type": "frame",
      "detail": {
        "direction": "in",
        "enc": "ratchet",
        "decrypt": "fallback_plain",
        "downgrade": true,
        "reason": "ratchet_miss"
      }
    },
    {
      "seq": 2,
      "ts": "2026-10-09T21:10:03+08:00",
      "type": "close",
      "detail": { "reason": "ws_disconnect", "frames_in": 1, "frames_out": 0 }
    }
  ],
  "downgrade_count": 1,
  "ledger_hash": "sha256:...",
  "signatures": {
    "initiator": "ed25519:...",
    "responder": "ed25519:..."
  }
}
```

### 3.2 四个必记字段（MVP 的最小集）

| 字段 | 取值 | 意义 |
|:--|:--|:--|
| `type` | `handshake` / `frame` / `close` | 事件类别 |
| `enc` | `ratchet` / `plain` | 本条用的加密档位 |
| `downgrade` | `true` / `false` | **是否发生降级**（核心告警位） |
| `did_verified` | `true` / `false` | 对端身份是否验过签名 |

> `downgrade: true` 这一位，就是让 10-09 那行静默的 `⚠️` 变成**账本里的一笔记录**。

### 3.3 防篡改：哈希链 + 双签

```
event[0].hash = H(session_id ‖ event[0])
event[n].hash = H(event[n-1].hash ‖ event[n])      ← 哈希链，改一条全断
ledger_hash   = event[last].hash
signatures.initiator = Ed25519_sign(私钥_发起方, ledger_hash)
signatures.responder = Ed25519_sign(私钥_响应方, ledger_hash)
```

**要点：**
- 单方改不了——**任一方单独重签，另一方签名对不上**
- 哈希链保证**删/改中间一条**会暴露（后续 hash 全断）
- **复用现有能力**：DID 签名、Ed25519 都已在 `agentlink/secure_session.py` / `crypto.py` 里

## 四、接入点（改哪儿）

> 原则：**最小侵入**，只在会话生命周期钩子上挂记录，不改加密逻辑本身。

| 接入点 | 文件（现状） | 做什么 |
|:--|:--|:--|
| ① 会话建立 | `agentlink/secure_session.py` 握手成功处 | 写 `handshake` 事件 + 起账本 |
| ② 每帧解密 | `secure_session.py` 的 `ratchet_decrypt` 及其回退分支 | 写 `frame` 事件，**降级路径必须落 `downgrade:true`** |
| ③ 会话关闭 | `agentlink/node.py` WS 断开处 | 写 `close` 事件 + 封账本（哈希链 + 双签） |
| ④ 账本存储 | 新增 `agentlink/ledger.py` | 追加式写入 `~/.agentlink/ledgers/<session_id>.jsonl` |
| ⑤ 查询接口 | 新增 CLI `agentlink ledger show <session_id>` | 只读，打印账本 |

> ⚠️ **关键：②号接入点是本设计的灵魂。**
> 10-09 那行 `回退普通解密` 所在的代码路径，**必须**写一条 `downgrade:true`。
> 找不到该路径 = 设计没落地。

## 五、验证方案（怎么证明它work）

复用现有脚本 `e2ee_cross_machine_verify.py` 的跨机链路，增加两项断言：

**验证 1：正常会话 → 账本无降级**
```
1. 跨机跑一次正常 @search（棘轮命中）
2. 取回账本 → 断言 downgrade_count == 0
3. 断言 signatures 双方均验签通过
```

**验证 2：强制降级 → 账本记到账**（回归 10-09 那个 bug 场景）
```
1. 人为制造棘轮未命中（如：跳过一条 ratchet 状态）
2. 取回账本 → 断言 downgrade_count >= 1
3. 断言该事件的 reason == "ratchet_miss"
4. 篡改账本中间一条 → 断言验签失败（防篡改测试）
```

**成功判据：验证 2 通过 = 10-09 的静默降级从此可查。**

## 六、与另外两个方向的关系

```
路②（社会层）内部分层：

   会话可审计（本文 · MVP · 先做）
        ↓ 提供「事实」
   冲突降级协议（第二步）
        ↓ 提供「裁决」
   反趋同设计（第三步）
```

**为什么必须先做可审计：**
- **仲裁**需要证据 → 证据来自账本
- **声誉**需要历史 → 历史来自账本
- **反合谋**需要可审计性 → README 里明写"反合谋（可审计性）❌ 缺失"

**可审计是另外两个的地基，且是三者中改动最小的（复用 DID 签名）。**

## 七、风险与坦白

| 风险 | 说明 | 缓解 |
|:--|:--|:--|
| 账本自身被改 | 若私钥全泄露 | 双签已挡单方；私钥泄露是终极风险，超 MVP 范围 |
| 存储膨胀 | 每帧一条事件 | 帧级事件可只记**异常帧**（正常帧不落），正常会话账本极小 |
| 拖慢会话 | 每帧写盘 | 改为**内存累积 + 会话结束一次性落盘** |
| 双方时间戳不一致 | 跨机时钟差 | 账本记双向事件，**不依赖单一时间源** |

> **诚实标注**：本设计**不解决** Anthropic 报告里的全部问题。
> 它只做一件事——**让"发生过什么"变得可查、不可抵赖**。
> 这是"社会机制"的第一步，不是终点。
