## 二、两份**不矛盾**，是**互补**——关键在"测什么"

**测评 A 测的是"代码有没有洞"** → 答案：有（假频道 E2EE、verify 可绕过、8x 处吞异常…）。
**测评 B 测的是"这东西值不值得存在"** → 答案：作为协议它有争议，作为"AI 辅助开发的思想实验"它合格。

→ **合并结论**：**代码有洞，但作者诚实 + 方向真实。**
- "有洞" = 工程成熟度不足（v0.5/v1.0 要补）
- "诚实 + 方向真实" = 项目的方法论价值已被两次独立测评共同确认

**两份都同意的**（共识，可信度高）：
1. 问题定位准（切入"平等同伴会话"这个空白）
2. 安全根基不牢（DIY 密码学、无 DH 棘轮、无外部审计）
3. 文档/工程规范优于同类入门项目
4. **不适合生产敏感数据**

## 三、⚠️ 两份各自的误判（必须标注，否则误导）

### 测评 B 的硬错
| 主张 | 实际 |
|:--|:--|
| "无 CI（大概率无 workflow）" | 🔴 **错**。`tests.yml` 存在，跑 3 版本矩阵 + 不变量断言 |

→ 教训：**看不到 ≠ 不存在**。它看到 `.github` 目录存在却看不到内容，就猜"大概率无"——典型的不看就断言。

### 测评 A 的"输入局限"（非模型错，是我喂的方式的局限）
- 我把源码**打散分批**喂（超长），导致模型**以为某些文件不存在**（如 `p1_shim.py`、`agentlink_p1.py`、`tests.yml`）→ 产生"文件不存在/造假"的**假阳性**
- 教训：喂超长源码给 LLM 时，**仓库结构信息也要一并给**，否则它会因"缺文件"误判

## 四、方法论沉淀（这才是两份结合的最大价值）

**🔴 核心发现：LLM 测评的结论，对"喂什么"极度敏感——同模型同日同项目，能给出差异很大的判断。**

由此得三条：
1. **"喂什么"决定"答什么"**：
   - 喂全码 → 得到**代码级**结论（准，但可能漏全局）
   - 只给链接 → 得到**项目级**结论（有定位价值，但事实易错）
2. **两种视角都要**：单一视角必偏。代码级漏"值不值得存在"，项目级漏"代码有没有洞"。
3. **LLM 测评的事实主张必须核**：两份都有事实错误（B 的 CI、A 的"文件不存在"）——**共同点是"缺信息时倾向猜"**。

**→ 标准做法（以后做 LLM 测评照此办）**：
> ① 明确标注"喂了什么"（全码 / 仅页面 / 仅 README）
> ② 事实类主张**逐条核验**，不采信推断
> ③ 至少两种视角（代码级 + 项目级）交叉
> ④ 把模型的"误判"也记录下来——它比正确部分更能说明模型的边界

**关联**：
- P-002（评估工具本身要先被评估）—— LLM 测评就是评估工具，它本身要先被评估
- P-007（记录工具的偏差方向取决于写的人怎么想）—— 喂什么/怎么问，决定它偏在哪
