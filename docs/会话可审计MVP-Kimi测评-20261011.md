# AgentLink 会话可审计 MVP — 批判性技术测评

**评审日期**：2026-10-11  
**评审对象**：《AgentLink 会话可审计 MVP 设计》v0.1  
**总体评级**：C+ —— 方向正确，但核心安全主张"单方改不了"在 MVP 边界内实际不成立；downgrade 判定缺乏独立见证，日志易沦为自我安慰。

---

## 一、真货（设计对在哪）

1. **事件触发点选得准**。将审计钩子植入握手成功、解密回退分支、WS 断开三个必经路径，覆盖了密钥生命周期和降级发生的真实代码位置。比起事后解析流量，源码级 hook 的 fidelity 高一个数量级。

2. **哈希链结构合理**。`H(prev_hash || event[n])` 的追加式账本，在数学上确实能保证：改中间一条 → 后续所有 hash 失效 → ledger_hash 变 → 签名失效。这是审计日志的标准做法（Certificate Transparency、blockchain 同源）。

3. **定位清醒**。明确承认这是"社会机制第一步"，不做实时告警和跨会话声誉，避免了过度工程。

---

## 二、硬伤

### H1. "单方改不了"是伪命题 —— 签名不交换等于没签

- **问题**：双方各自对 ledger_hash 签名后，**方案未说明签名是否交换、是否持久化保存对方签名副本**。
- **为何是问题**：如果 Alice 和 Bob 各存一份账本，Alice 事后删改自己的账本、重新计算 hash 链、用自己的私钥重签，她本地的账本仍然"验签通过"。由于 MVP 没有"双方对账"或"共识锚定"机制，Bob 永远无法知道 Alice 的账本已被篡改。
- **后果**：核心安全主张"单方改不了"在单点存储场景下不成立；账本只是"本地自嗨"。
- **怎么改**：会话结束时**强制交换**双方对最终 ledger_hash 的签名，各自持久化保存对方签名。后续任何一方声称的账本，必须同时出示"自己的签名 + 对方的签名"，缺一则视为无效。这是把"双签"从仪式变成机制的最小改动。

### H2. 签名只签 ledger_hash —— 中间篡改的检测成本被低估

- **问题**：签名只覆盖最终 ledger_hash，验证时需要从 event[0] 逐条重算 hash 链直到最后一环，才能确认没被篡改。
- **为何是问题**：没有明确说明的**增量验证/缓存机制**。随着会话变长，验证复杂度 O(n)。更隐蔽的是：如果攻击者（拥有私钥）删掉中间 100 条事件后重新 hash，验证者必须拥有"完整预期事件序列"才能发现缺失 —— 但验证者从哪拿到预期序列？
- **后果**：hash 链的 tamper-evident 属性是存在的，但 tamper-detection 依赖于"拥有完整原始数据"，而原始数据恰好是被攻击者控制的那份。
- **怎么改**：每条事件除 ledger_hash 外，增加**独立签名**（或用 Merkle tree 提供 inclusion proof）。或者至少：定期将累计 hash 通过第三方信道（如 QQ 消息）发送出去，形成外部锚定。

### H3. downgrade 判定缺乏独立见证，误报/漏报风险并存

- **问题**：降级判定由 `ratchet_decrypt` 的回退分支触发，即**被审计代码自行报告自己是否降级**。棘轮未命中的原因可能是：正常重传、乱序、实现 bug、内存状态不一致、或真实攻击。
- **为何是问题**：没有独立观察者区分"合法解密失败"和"恶意降级"。如果攻击者通过某种方式（如内存篡改、API hook）让降级发生但绕过审计 hook，审计日志不会记录；反之，正常的网络抖动导致棘轮状态漂移也可能被记为 downgrade，形成误报。
- **后果**：downgrade_count 的数值含义模糊，不能作为"安全事件"的可靠指标；长期看会导致告警疲劳或虚假安全感。
- **怎么改**：引入**降级原因分级** —— `ratchet_miss` 细分为 `local_state_mismatch`（本地状态问题）、`reordered_frame`（乱序）、`potential_downgrade`（真正可疑）。同时，将加密档位（cipher suite）作为每条 frame 事件的独立字段记录，即使 ratchet_miss 被绕过，事后仍可通过"档位突变"（如从 ChaCha20 变成明文）发现异常。

### H4. "只记异常帧"直接摧毁审计完整性

- **问题**：风险坦白中提出"缓解:只记异常帧"，但正文的 events 数组明显设计为记所有 frame。
- **为何是问题**：如果只记异常帧，攻击者的最优策略就是让攻击行为**不触发异常检测**。例如：攻击者通过 pre-computation 让棘轮同步到预期状态，从而避免 ratchet_miss；或者攻击直接发生在传输层之下（如截断 WS 连接），根本不经过解密逻辑。
- **后果**：审计日志从"完整证据链"退化为"采样监控"，无法支持事后的事无巨细复盘。
- **怎么改**：MVP 阶段**必须全量记录所有 frame 事件**（哪怕只记 hash 和 metadata，不记 payload）。存储膨胀通过**自动归档**（会话结束 7 天后压缩到冷存储）解决，而不是通过丢弃事件解决。

### H5. 时间戳不可靠，但方案对因果顺序的处理不够明确

- **问题**：`started_at` 和 `ts` 使用本地时钟，跨机存在漂移；events 数组虽然按追加顺序排列，但 jsonl 文件可被离线重排。
- **为何是问题**：如果 Alice 事后重排事件顺序再重新 hash，由于 hash 链的输入是 `prev_hash || event[n]`，重排会导致 hash 全变 —— 但她可以用自己的私钥重新签名。如果对方没有保留原始时间戳和签名副本，无法证明事件被重排。
- **后果**：时间顺序的不可篡改性依赖于签名交换（回到 H1），但 H1 未解决。
- **怎么改**：在每条 event 中加入**逻辑时钟**（如 hybrid logical clock 或至少单调递增的 seq），并将 seq 纳入 hash 链输入。这样即使离线重排文件，seq 的连续性会暴露篡改。

### H6. DID 身份验证与账本记录的时序 gap

- **问题**：handshake 事件记录 `did_verified`，但如果 DID 验证本身被绕过（如中间人提前注入公钥），后续所有"双方签名"都是和攻击者签的。
- **为何是问题**：账本的可信根基是 DID 绑定，但方案没有说明 DID 验证的详细流程和失败处理。
- **后果**：底层身份被攻破时，上层审计日志自动失效，但日志本身会给人虚假安全感。
- **怎么改**：在 handshake 事件中**完整记录 DID 验证的输入输出**（包括挑战-响应的 nonce、验证通过的公钥 fingerprint），使事后可以独立复核 DID 验证步骤。

## 三、设计缺口（方案没想到但该想到的）

1. **缺少"审计日志的审计日志"（meta-audit）**。谁确保 `ledger.py` 本身没被篡改？如果攻击者替换 `ledger.py` 为 no-op，整个审计体系静默失效。至少应记录 ledger 文件本身的 hash 到系统日志（macOS unified log / syslog），形成外部 witness。

2. **没有 replay 保护**。ledger 文件是本地 jsonl，攻击者可以把**旧会话的合法账本**复制到新会话路径下，伪装成新会话的审计记录。方案没有将会话上下文（如双方 IP、端口、WS connection ID）绑定到账本中。

3. **CLI `ledger show` 的权限模型缺失**。如果多用户共享一台 Mac，ledger 文件默认权限是什么？其他进程能否读取？DID 私钥是否从 keychain 安全读取？

---

## 四、如果只能改一处

**强制在会话结束时交换并持久化保存对方对最终 ledger_hash 的签名**。

这是把"双签"从形式要件变成实质约束的唯一最小改动。没有这一步，所有 hash 链和 Ed25519 签名都只是本地自嗨，审计价值为零。具体做法：在 close 事件后增加一个 `exchange_signatures` 步骤，双方通过已有 WS 信道交换签名，各自保存为 `<sid>.jsonl.sig`，任何一方后续出示账本时必须同时提供双方签名。

---

## 五、最终建议

**建议：做，但改完再做。**

当前方案是一个"正确的骨架，但关键韧带没接上"。直接实施会导致：花了工程成本，却得到一个无法支持事后问责的审计系统 —— 这是最差的投入产出比。

**改成什么样**：
- **P0（必须）**：修复 H1（签名交换）、H3（降级分级）、H4（全量记录）。这三条不解决，审计系统不可信。
- **P1（强烈建议）**：修复 H2（增量验证/Merkle tree 或外部锚定）、H5（逻辑时钟）。
- **P2（可选）**：补充设计缺口的 meta-audit 和 replay 保护。

MVP 的边界可以保持不变（不做实时告警、不做声誉），但边界内的实现必须**真的做到不可篡改**，而不是"看起来不可篡改"。
