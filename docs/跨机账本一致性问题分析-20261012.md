# 跨机账本一致性问题分析（v0.3 输入）

> 日期：2026-10-12 ｜ 状态：**分析稿（待评审）**
> 上游：v0.2 会话账本（`docs/会话账本-v0.2接入完成报告-20261011.md`，主链路已接通、40 测试全过）
> 触发：2026-10-12 真机跨机回归（`agentlink_call_peer.py`）时暴露的真问题
> 定性：**这不是实现 bug 的补丁点，而是设计假设与实现模型之间的结构性矛盾。** 不改设计，补丁只会再打一次"调用侧假修复"（沿用 10-09 教训）。

---

## 〇、一句话结论（先看这个）

**v0.2 的 H1 签名交换在跨机场景下"结构性失效"**——不是偶尔失败，而是**诚实会话也必然失败**。

根因：**设计假设「双方共用一个 ledger_hash」，实现却让「双方各自独立生成账本、各签各自的 hash」。**
两个 hash 在数学上几乎不可能相等（账本内容按视角天然不同），于是双签校验里
**对方签名永远对不上我这边的 hash** → 每次都判 `signature verification failed`。

> 类比：两个人各写一份会议纪要，然后约定"用对方的签名证明我的纪要没被改"——
> 但对方签的是**他自己那份纪要**的指纹，不是我的。签名再真，也证明不了我的那份。
> H1 想解决"单方改账本"，却因为没有**共同的签名对象**，退化成了比不交换更糟的状态（**假阴性**：真会话被判 tampered）。

## 一、问题现场还原（代码级）

### 1.1 双方各自建的账本，内容天然不同

`SessionLedger` 在 `secure_session._start_ledger()` 里**每端各起一本**（`secure_session.py:125`）。
两本账本在以下字段上**必然不同**：

| 字段 | 发起方（Alice） | 响应方（Bob） | 是否相同 |
|:--|:--|:--|:--:|
| `initiator` | 自己 DID | 占位/对端 DID（代码注释"调用方后补"） | ❌ 可能不同 |
| `responder` | 对端 DID | 自己 DID | ❌ 可能不同 |
| `started_at` | Alice 本地时钟 | Bob 本地时钟 | ❌ 不同 |
| `events[i].ts` | Alice 本地时钟 | Bob 本地时钟 | ❌ 不同 |
| `frame.direction` | out = Alice 发出 | out = Bob 发出（镜像） | ❌ 相反 |
| `handshake.nonce/fpr` | Alice 视角取值 | Bob 视角取值 | ❌ 不同 |
| `close.reason` | `remote_hangup`/`disconnected` | `hangup:...` | ❌ 不同 |
| 帧数量 | 本端观察到的 in/out | 本端观察到的 in/out | ❌ 常不同 |

哈希链把上述**所有字段**（`seq/ts/type/detail` 全量）都纳入输入（`ledger.py:_hash_input` + `_append`），
所以：

```
H_A = 链(Aliced账本所有事件)   ≠   H_B = 链(Bob账本所有事件)      ← 几乎必然
```

**这不是"篡改"，是两个诚实节点在不同视角下的自然结果。**

### 1.2 签名对象错配：各签各的 hash

`node._finalize_ledger()`（`node.py:350-390`）：

```python
# Alice 端
pre_hash = led.events[-1].hash          # = H_A（Alice 自己的链尾）
my_sig   = sign(A私钥, pre_hash)         # sign(A, H_A)
await ws.send({"ledger_hash": pre_hash, "sig": my_sig})   # 把 H_A 和签名都发过去

# Bob 端（对称）
pre_hash = led.events[-1].hash          # = H_B（Bob 自己的链尾）
my_sig   = sign(B私钥, pre_hash)         # sign(B, H_B)
```

**问题**：`ledger_sig` 消息里带的 `ledger_hash` 字段**只用于告知，不参与任何校验、不落盘、不比对**
（`node.py:469` 收到后只取 `msg["sig"]`，`ledger_hash` 直接丢弃）。

于是 Alice 落盘时：

```python
led.attach_signatures(initiator_sig = sign(A, H_A),
                      responder_sig = sign(B, H_B))     # ← 对端签名签的是 H_B
```

### 1.3 验签必然失败（假阴性）

Alice 之后调 `ledger.verify(verifier=...)`（`ledger.py:267`）：

```python
vi = verifier(signatures["initiator"], self.ledger_hash, "initiator")  # sign(A,H_A) vs H_A  ✅
vr = verifier(signatures["responder"], self.ledger_hash, "responder")  # sign(B,H_B) vs H_A  ❌
```

第二条用**自己的 ledger_hash（H_A）**去验**对端签名（签的是 H_B）**。
除非 H_A == H_B（1.1 已证几乎不可能），否则 **必然**返回：

```
{'ok': False, 'sig_verified': False,
 'reason': 'signature verification failed (tampered or wrong signer)'}
```

**结果**：一次完全诚实、毫无篡改的跨机会话，双签校验**必然判"疑似篡改"**。

> 🔴 **这比"不验签"更危险**：不验签只是没保护；错误验签会**制造假警报**，
> 让"篡改检测"这个刚建的机制**信用归零**（狼来了）。且与 H3 分级联动时，
> 会不断产出 `critical` 级 `signature_verify_failed` → 触发告警疲劳（v0.2 刚要避免的反面）。

## 二、根因：设计假设 vs 实现模型的三处断裂

### 断裂 1：签名对象不唯一（核心）

- **v0.2 设计 §3.4** 写的是「双方**各自计算 ledger_hash** → 交换签名 → 谁主张谁举证的**对方签名**来佐证」。
- 但没说清：**到底签哪个 hash？** 设计文字暗含"存在一个双方都认的 ledger_hash"（"若 hash 不一致 → 暴露篡改"）。
- **实现**却让每端签**自己的** hash。于是"对方的签名"证明的是**对方那份账本**，与我这份无关。

> **断裂本质**：把「一份共同文档的双签」的模型，套在了「两份独立文档」的实体上。
> 双签机制要求**唯一签名对象**；两本账本 = 两个对象 → 机制不成立。

### 断裂 2：两本账本没有"规范同一"步骤

真正的分布式可审计系统（如 Certificate Transparency、区块链）都有一条铁律：
**先定义唯一规范串（canonical form），再对规范串签名/哈希。**

v0.2 有 `_canonical_json`（保 key 排序），但**只作用于"事件内部字段"**，
没有解决**跨机两本账本如何归一到同一个可比较对象**的问题。
结果：`initiator/responder/ts/direction/非对称事件` 全在哈希输入里，
两本永远归不了一。

### 断裂 3：设计的"防分叉"判据无实现支撑

设计 §3.4.3 说「若 Alice 与 Bob 手中的账本 hash 不一致 → 立刻暴露有方篡改」。
**实现里没有任何地方拿两个 hash 做比对**（对方 `ledger_hash` 字段收到即弃）。
所以这条判据**目前是纸面条款**——既没生效，也因断裂 1 无法生效。

## 三、影响面

| 影响 | 说明 | 严重度 |
|:--|:--|:--:|
| H1 机制失效 | 跨机诚实会话双签校验必然 false → 核心卖点"不可篡改"不成立 | 🔴 高 |
| 假阳性告警 | 每次会话都产 `signature_verify_failed`(critical) → 告警疲劳 | 🔴 高 |
| 离线验证依赖本地 | `verify()` 只能在**生成它的那台机器**上通过（因只认本地 hash）→ 第三方复验不可行 | 🟠 中 |
| 防分叉纸面化 | §3.4.3 无实现 → 分叉检测缺失 | 🟠 中 |
| 回归验证阻塞 | v0.2"验证 1/3"（正常会话双签齐备、单方篡改验签失败）在真机**跑不出期望结果** | 🟠 中 |
| 前端/CLI 误导 | `ledger show` 会打印"单方出示无效/验签失败"，把正常会话标成可疑 | 🟡 低但伤信任 |

> 注：10-12 真机回归里，对方是**旧版 responder**（不回 `ledger_sig`），
> 走的是"超时 → 单签"路径，**暂时掩盖**了本问题。
> 一旦双端都升级到 v0.2，**问题会立刻全面暴露**。本分析正好卡在这个时间窗前。

## 四、v0.3 修复方案（三选一，附取舍）

### 方案 A：单账本 + 镜像补记（★ 推荐）

**思路**：会话只产**一本规范账本**，由双方视作同一文档。

1. 定义**规范视图（canonical ledger view）**：以规范规则把两端的观察**归并**成唯一事件序列：
   - 排序键：`(逻辑时钟, 端标识, 帧序号)` 而非本地 wall-clock
   - `direction` 归一为**发送方 DID**（而非 in/out 视角词）
   - 握手 nonce/fpr 取**发起方**值（两侧都记发起方视角）
   - `initiator/responder` 由**会话协商时确定并双方一致写死**（修 §1.1 第 1、2 行）
2. 会话结束：双方各自按同一规范规则计算 `H_canonical`
3. 交换：`sign(私钥, H_canonical)`，**签名对象同一个**
4. 校验：`verify` 用 `H_canonical` 验双签 → 诚实会话 ✅ 通过

**改动量**：中。核心在 `ledger.py` 增加 `canonicalize()` + 归一字段规则；`node.py` 交换的 `ledger_hash` 字段改为**参与比对**。
**风险**：规范化规则若不完备，两端仍可能算出不同 `H_canonical` → 需**对账自检**兜底（见方案 C）。

### 方案 B：交换"对端账本哈希"只做防分叉，双签改签"本端+对端"拼接

**思路**：承认两本账本不同，签名对象改为 `H(local_hash ‖ peer_hash)`。

1. 交换时**保留**对方 `ledger_hash`（现在被丢弃的字段）
2. 签名对象 = `sha256(my_hash ‖ peer_hash)`（顺序按角色固定）
3. 双签校验：用**拼接对象**验双方签名 → 两侧都能复算同一对象

**改动量**：小（改签名对象计算 + 保留对端 hash 字段）。
**优点**：改动最小，且顺带**实现 §3.4.3 防分叉**（双方 hash 都进了签名对象，任一方改本端或对端 hash 都验不过）。
**缺点**：签名对象是"两本的拼接"，语义上是"共同认知峰值"而非"某本账本"，文档/三方复验时要解释清楚。

### 方案 C：双账本 + 对账协议（重）

**思路**：明确承认"两端各持一本、内容不同"，新增**对账（reconcile）步骤**：
交换后比对双方"事件集合摘要"（如 Merkle 根），分歧则各自补记差异事件。

**改动量**：大（引入 Merkle / 差异补记，接近 P1）。
**取舍**：**与此前"P1/P2 私网场景暂缓"的既定判断冲突**，除非目标用户扩到多方/不可信对端，否则不急。

## 五、推荐路径与理由

**推荐：方案 B 打底 + 方案 A 的"规范字段"局部采纳（混合）。**

理由：

1. **B 用最小改动同时修好"双签失效"+"防分叉缺失"两件事**——这正是 v0.2 未兑现的两条核心承诺。
2. 但 B 没消除"两本账本内容不同"的**根本认知负担**；把 §1.1 里最扎眼的三个字段
   （`initiator/responder` 写死、`direction` 归一到发送方 DID、握手 nonce/fpr 统一取发起方视角）
   **顺手规范化**，成本低、收益大，让两本账本"结构上更接近"，减轻未来任何对账方案的压力。
3. **不做 C**——符合"私网自用、P1/P2 暂缓"的既定判断。

**v0.3 最小验收标准（可测）**：

```
验证 A：诚实跨机会话
  双端均 v0.3 → 双签校验 ok=True（断：修复假阴性）
验证 B：单方改本端账本重签
  对方 hash 变了 → 拼接对象变 → 对方签名验不过 → ok=False（断：防篡改仍有效）
验证 C：单方改对端 hash 记录
  签名对象变 → 本方签名也验不过 → 暴露（断：防分叉落地）
验证 D：对端 ledger_hash 字段确实参与校验（不再是死字段）
```

## 六、附带发现（本次一并记录，不扩大范围）

1. **`initiator` 占位未补**：`secure_session.py:139` `initiator` 取的是"对端 DID 或占位"，注释"调用方后补"——
   响应方建的账本 `initiator/responder` 语义可能整体反了。**即使不修哈希问题，这也会让账本字段失真。**
2. **对方 `ledger_hash` 字段收到即弃**（`node.py:469`）——既是断裂 3 的直接证据，也是方案 B 的落点。
3. **10-12 真机暴露的 IPv6/IPv4 WS 不兼容**（`agentlink_call_peer.py:_force_ipv4` 注释）：
   本端 IPv6 优先、对端 WS 只监听 IPv4 → 主机名连 WS 必超时。**属通联层，与账本无关，单列待办。**
4. **对端 IP 漂移**（`peers.json` 注释：DHCP `.3 → .217`）→ 已由"一律用主机名 + Bonjour"缓解，
   但**脚本仍有 `AL_MY_IP` 等硬编码兜底**（示例 `192.0.2.11`），换网需同步改多处 → 复用 P-004 教训。

## 八、诚实边界（沿用 v0.2 的坦白）

- 本分析**只覆盖"跨机账本一致性"**，**不解决** v0.2 已标注的"被审计代码自报"根本局限（需独立见证，P2）。
- 私钥泄露、交换信道被劫持两项**依然未解决**（超 MVP 范围），与本问题正交。
- 本分析基于**代码静态推演**（`ledger.py` / `node.py` / `secure_session.py`）+ 10-12 真机部分现象；
  **尚未跑"双端 v0.3 诚实会话"的实测**（需对端同步升级）——方案验证留到 v0.3 实现后。
