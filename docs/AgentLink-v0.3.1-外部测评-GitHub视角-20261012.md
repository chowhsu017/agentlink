### AgentLink 项目测评

一句话定位：一个"Agent 对 Agent"的实时通信协议 + 参考实现（纯 Python），覆盖会话生命周期（呼叫→振铃→接通→数据帧→心跳→挂断）、E2EE、信令发现、频道/Presence。作者自述"不会写代码，用 AI 做出来的"，这个背景本身就是项目最大的看点。

#### 基本信息

| 项 | 情况 |
|:--|:--|
| 创建时间 | 2026-08-05，至今约 2 个月，更新活跃（最近 push 就在今天） |
| 规模 | 纯 Python，12 个模块文件，单文件偏大（node.py 39KB、p2.py 38KB） |

| 文档 | README 详尽 + 协议草案 + CHANGELOG + REVIEWS，文档质量显著高于代码量 |

#### 优点（诚实说，不少）

1. **问题选得准。** 当前多智能体协作的痛点确实是"协议碎片化"：MCP 是工具调用范式，A2A 偏任务委派，而这个项目瞄准的是"平等同伴之间的连续会话"。README 引用 Anthropic 2026-08 的多智能体研究报告来论证定位，说明作者做过功课。
2. **安全自审异常坦诚。** 这是整个仓库最亮眼的部分：明确列出"无完整前向保密、对称棘轮是假的（链尾密钥不更新）、DIY 密码学、无第三方审计、不适合生产敏感数据"。v0.3.1 还主动废除了自己原来"假加密"的频道 E2EE——很多成熟项目都做不到这一点。
3. **工程意识在线**：防重放（nonce + seq 窗口）、状态机（转换表 + 非法转换抛异常）、挑战-响应鉴权、SQLite WAL、不变量断言防降级。CHANGELOG 记录了两台 Mac 联调暴露并修复 5 个协议缺陷——说明真跑过，不是纸面项目。
4. **上手门槛低**：pip install + agentlink serve 一行起服务，CLI 齐全，跨平台。

#### 缺点与风险

1. **安全根基不牢。** E2EE 是自研的（X25519 + HKDF + ChaCha20-Poly1305，但缺 DH 棘轮），密码学界共识是此类协议应直接用 Noise/libsignal——README 自己也承认。没有第三方审计前，不应承载任何真实敏感数据。
2. **单点依赖作者 + AI。** 作者不会写代码，意味着代码可维护性依赖 AI 辅助；没有贡献者，无 CI 信息（.github 目录内容未知，大概率无 workflow）。单文件近 40KB 也提示模块化不足。
3. **生态位尴尬。** 要通信为何不用 libp2p？要 Agent 互操作为何不用 A2A / MCP？它的差异化"会话原语"其实可以跑在现有传输之上，目前看不到非它不可的理由。
4. **README 自我引用过多**："DeepSeek 评价"是提示词生成的评价而非真实背书；大量引用 Anthropic 报告来拔高定位，营销味略重。
5. 作者自己列出的架构级空白：无声誉体系、无仲裁/降级机制、无反合谋可审计性——README 诚实承认"提供的是通道，不是社会机制"。

#### 总评

| 维度 | 评分（5 分制） | 说明 |
|:--|:--:|:--|
| 问题定位 | ⭐⭐⭐⭐ | 切入点真实且尚未被标准答案占据 |
| 代码质量 | ⭐⭐⭐ | 能跑、有测试、状态机规范，但单文件臃肿、DIY 密码学 |
| 安全 | ⭐⭐ | 自审坦诚加分，但无棘轮、无外部审计，不可用于生产 |
| 文档/工程规范 | ⭐⭐⭐⭐ | CHANGELOG、协议草案、已知缺陷清单齐全，超出入门项目水准 |
| 生态成熟度 | ⭐⭐ | 无人使用，与 libp2p/A2A/MCP 相比无 compelling reason |

**结论**：这是一个思想实验价值大于工程价值的项目——它真正回答的问题不是"agent 怎么通信"，而是"一个不会写代码的人，能否用 AI 做出一个可被审查、可被使用的协议实现"。从这个角度看，答案是合格的，甚至超出预期。作为基础设施采用则为时过早，建议观望其 v0.5（频道 E2EE 重写）和是否引入 Noise 协议、是否出现除作者外的真实用户。
